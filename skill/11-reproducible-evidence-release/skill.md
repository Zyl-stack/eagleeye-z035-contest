# 模型、程序和演示的可复现发布

## 适用范围

适用于比赛资料整理、队友交接、报告绑定版本和公开仓库准备。此技能提供版本核对与本地打包流程，发布、推送及对外沟通由使用者另行执行，第三方许可沿用原声明。

## 工作流

1. 先盘点现有代码、README、训练日志、模型、库、导出脚本、硬件与应用包，避免重做已有实现。分清任务路线、模型变体、输入尺寸和类别表，不把不同文件因同名当同版。
2. 对模型追溯基座权重 URL/版本/哈希、团队训练/微调/QAT记录、数据版本及划分、导出配置、优化器/运行库版本。训练命令文件只证明存在流程，成功训练还需日志和产物链。
3. 绑定报告版本：代码 commit+dirty 状态、关键源码 hash、模型 hash、可执行 hash、XSA/bitstream hash、启动镜像、配置及输入。as-built 稳定版与开发版分别归档，不能直接用 HEAD 替代旧二进制对应源码。
4. 建证据表：源码存在、语法/单测、主机运行、RTL、实现报告、QEMU、用户上板反馈、原始板端日志、演示录像分别列出。每项结论绑定对应输入、程序和时间；模板、模拟输出不能填作实测。
5. 审计 `git ls-files`、忽略规则、子模块和 Git LFS。`runs/`/`build/` 内权重或结果若被忽略，给出独立交付位置/hash及授权状态，不能让接收者仅靠切分支获取不存在的产物。
6. 分开核对代码、权重、数据、示例图片和第三方库的许可及 NOTICE；分别判断比赛提交与公开再分发是否有可引用依据。源码 Apache/MIT 不能无证据覆盖外部权重/数据；unknown 填“待确认”，不自创许可。
7. 用 [assets/release-record.json](assets/release-record.json) 记录身份与状态，生成文件清单并从干净解压目录检查。manifest 工具只检查文件身份和完整性，不验证授权或性能。
8. 让复现者依据说明执行最小确定输入、比对 Golden，再执行所需真实硬件验收。缺原始板端日志时保留缺口，不为填报告重新制造“预期实测”。

## 使用方法

在待发布目录之外保存 manifest，避免自引用：

```sh
python scripts/manifest.py create deliverables release-manifest.json
python scripts/manifest.py check deliverables release-manifest.json
```

check 会拒绝遗漏、修改、新增文件和不安全路径。大工程先整理只含授权交付物的 staging 目录；不要直接把整个工作区或对话记录打包。

## 失效条件

没有程序/模型哈希、只凭文件名或分支名绑定、把旧 raw/JPEG 结果混用、当前演示无日志却推定运行最新源码、404 就判定仓库不存在，均需要补证据。无法确认时用“待确认”或“暂无”，并指出缺哪一环。

## 已验证效果与失败来源

[E11](../evidence.md#e11发布身份必须细化到文件)：XS-320 官方模型、S-416 QAT 训练、GridPolicy/AttentionPolicy 多路线并存，暴露仅用“PicoDet/最终版”命名无法复现的问题。已有程序和接口不重复提供，只给来源位置与明确状态。本技能新增 manifest 工具在 [VALIDATION.md](../validation.md) 中记录验证。

## 可直接使用的提示词

> 请依据现有文件和历史记录审计本次比赛发布，不重做已有程序。为模型来源、训练、数据、授权、硬件和最终应用建立证据表，逐文件给 hash 并区分 as-built/开发版。分别说明比赛提交、公开再分发的依据；不清楚直接写待确认。完成可复现 staging 与校验清单，记录尚缺的板端证据。
