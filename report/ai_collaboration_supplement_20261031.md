整理日期：2026年10月31日。历史资料按当前 PicoDet 工程提交范围整理，案例编号沿用来件。

## 一 记录范围与协作分工

本文按“提示词、模型回答、自我纠错轨迹、智能体工作流设计”整理 EagleEye 项目的代表性协作。项目从 Lanczos 图像缩放逐步发展为摄像头采集、PS 检测、注意力与 ROI 选择、PL 局部重采样以及交互显示组成的仿生视觉系统。不同阶段涉及 AX7020 与 Z035，不能把不同板卡、模型和演示版本的结果混为一体。

团队负责确定需求、提供工程与测试输入、完成接线和板端操作、反馈画面与日志，并决定是否采纳修改；队友按分工提供 IP、算法和接口。大模型参与需求拆解、源码修改、日志分析、参考数据生成、工程核对和文档整理。模型生成的方案需要通过工具结果与人的实物反馈验收。

## 二 预处理 IP 的需求与验证

### R01 从功能要求到可独立重建的源码包

来源 1，聊天“实现 PicoDet FPGA 图像预处理 IP”，2026年10月17日。用户在提示词中同时给出器件、时钟、数据格式、插值规则、工具版本和验收方式，使模型的输出能对应明确的工程检查项。

**提示词原文节选**

“请帮我实现一个完整、可独立验证的 FPGA 图像预处理 IP，用于 EagleEye Z035 板上的 PicoDet 摄像头推理链路。”

“输入是一帧 640×360 RGB888 图像，通道顺序 R、G、B，每行跨度 1920 bytes。输出完整的 PicoDet 输入张量：1×3×320×320、FP32、NCHW。”

“.xci、DCP、.bit、.xsa 可以作为附加参考，但不能作为唯一交付物。请不要修改现有摄像头、VDMA、HDMI、OSD、Fovea 模块或它们的地址映射。”

**模型回答原文节选**

“核心 RTL 和控制接口已经落地。插值权重可精确表示为整数分数，归一化则由随源码交付的 FP32 查找表完成；这样无需在 FPGA 中放置通用浮点除法器。”

“从干净压缩包解压后，Vivado 2024.2 已成功重新打包，证明交付包不依赖原工程目录。原先的五帧与联合仿真均已通过；本机的 Icarus 12 开发版在重复编译时出现间歇性进程崩溃，我正在补一条 Vivado 仿真路径，方便你在 2022.2 环境直接复验。”

### 纠错与验证轨迹

初始方案以 RGB 流和三个输出通道实现处理核心，随后补上 32 位 DMA 输入适配器，确保 DDR 字节流能正确重组像素，并进行适配器与核心联合仿真。验证从“核心能运行”扩展到完整张量的数值、通道顺序、边界和背压握手。

重复编译遇到仿真器进程崩溃后，模型没有把该现象直接解释为 RTL 数值错误，而是补充 Vivado 仿真路径。交付前又从干净压缩包重新打包，以检查绝对路径和原工作区依赖。

历史回答报告五类帧的每帧 307200 个 FP32 值与 Golden 逐位一致；独立 IP 在 Vivado 2024.2、XC7Z035、100 MHz 下实现，WNS +3.519 ns。7.889 ms 是带测试背压的流接口仿真时间。它们不能替代 Vivado 2022.2 复跑、板端 DDR 总延迟或检测框变化验收。

**产物与人的验收**　Qiansai/picodet_preproc_ip/ 中保存 RTL、ROM、testbench、Golden、脚本及报告；团队负责在目标工具重建、集成 DMA、处理缓存一致性并上板测量。
## 三 实时推理与运行环境

### R02 将单图推理接入现有摄像头链路

来源 2，聊天“实现 AX7020 实时 PicoDet 推理”，2026年10月6日至7日。

**提示词原文节选**　“我需要在 AX7020 上实现：OV5640 640×360 实时采集保持原有 HDMI 显示，同时 PS 端 PetaLinux 从 DDR 取得最新完整帧，运行 Paddle-Lite PicoDet-XS 320，持续输出 PERSON bbox 和实际 FPS。”

**模型回答原文节选**　“QEMU Cortex-A9 端到端推理验证：检测到 6 个 PERSON”

“而 XSA 明确由 Vivado 2022.2 生成，不能交给 PetaLinux 2017.4 导入。”

**纠错轨迹**　用户要求同时交付镜像、程序和真实板端日志。模型完成源码、ARM 程序、设备树和脚本后，环境预检发现 petalinux-create 不可用，因而把可交付源码与尚不能生成的启动镜像分开报告。QEMU 结果只证明离线程序与模型链路运行，不能当作板卡 FPS 或上板联调。

历史方案采用“最近完成槽→复制到私有内存→复查写指针”。后续工程复盘进一步指出：环形指针前后相同仍可能经历多次回绕，需增加复制时间界限、单调帧序号或缓冲所有权保证。私有快照是设计方向，不能仅凭两次指针检查宣称并发读取绝对安全。

**证据**　team_handoff_20261005_v1/DELIVERY_README.md；integration/linux_ov5640_picodet/；deliverables/logs/qemu_offline_validation.log。快照限制见[技能经验](../skill/evidence.md)的 E05。

## 四 模型与演示版本核对

### R04 区分注意力匹配和稳定跟踪

来源 3，聊天“回答项目复现问题”，2026年10月27日。

**提示词原文节选**　“① 当前板上实际运行的是稳定的 GridPolicy 版、后续 AttentionPolicy 版，还是另一版程序？② PicoDet 之外是否还有独立的目标跟踪、稳定 target_id 或检测结果输出接口？”

**模型回答原文节选**　“因此最新有上板反馈的是 AttentionPolicy，但包内没有当次原始串口日志或板卡现状快照，无法独立确认**此刻**板上运行的仍是哪一版。”

“JSON 中没有 `target_id`”

**纠错轨迹**　核对从“目录中有新程序”推进到“源码、应用归档、部署说明和当次日志是否对应”。AttentionPolicy 用相邻结果中心距离作本地人员匹配，无检测时清空历史，因此不能把本地 target_id 写成跨遮挡稳定跟踪。

**证据**　复现包 src/ps_as_built/、src/ps/src/fovea_roi.hpp、src/ps/src/paddle_person.cpp 和 board/attention/README.md。历史 CPU attach_100.log 不作为当前注意力版运行日志。

### R05 训练记录不等于交付权重来源

来源 4，聊天标题、回合及时间见[来源摘录](ai_collaboration_excerpts_20261031.md)，2026年10月29日。

**提示词原文节选**　“请帮忙确认当前 model.nb 的原始权重来源、是否经过训练或微调、所用数据来源，以及比赛提交和公开仓库再分发是否有适用授权；”

用户随后补充：“你也要参考一下我本地的训练记录”

**模型回答原文节选**　“会。我会把本地训练记录和仓库说明对照，重点看记录中的产出是否能对应到这份 `model.nb`，避免把其他 PicoDet 训练实验误认成最终演示权重。”

“型号、输入尺寸和产物名均与交付的 `model.nb` 不同，不能据此称交付权重经过微调。”

**纠错轨迹**　模型起初依据交付 README 说明 XS-320 官方模型来源；用户提醒后加入本地训练记录，区分 XS-320 的 model.nb 与 S-416 量化训练的 picos416.nb。核对由“项目是否训练过模型”转为“这份权重对应哪条训练与转换链路”。历史公开仓库访问失败只表明当时无法核对，不能推断仓库不存在或目前仍不可访问。

**结果与边界**　历史回答对权重用途授权及最终现场版本保留待确认。上述是历史核对结论，不作为本轮重新完成的许可审查。来源路径为 Qiansai/交付文件/paddle_person_ax7020/README.md 与 Qiansai/README.md。
## 五 视频显示与交互的返工

以下 R06、R07 均来自既有工程复盘。用户原话由既有复盘转录，模型处理以摘要呈现；原始回合和前后对照画面未随交接资料提供。

### R06 暂停后切换模式导致 HDMI 黑屏

**用户反馈节选**　“这次按了key0就黑屏”。复盘记载复现条件包括暂停后按 KEY0、整个 HDMI 黑屏、只能断电重启；单按 KEY1 暂停则可保持画面。

**模型处理摘要**　将现象分解为暂停、模式切换、视频输出和推理进程四个观察点。串口仍有 SNAPSHOT/TIME 时，不能把整个显示故障直接归为 PicoDet 停止；排查优先转向视频输出状态、帧边界和模式切换逻辑。

**纠错轨迹**　早期修改未满足暂停与切换组合的要求。用户继续明确播放态、暂停态以及从不同插值模式进入暂停后的循环规则；模型将这些反馈转成 roi_mode_policy 的状态转移。后续需把模式状态、OSD 文案与帧生效时机一起验证。

**人的操作与证据**　队员复现按键顺序、更新 Vivado module reference、实现并上板观察。工程复盘记载最终模式与状态文字可用，但连续串口录像尚缺。对应 RTL 为 video_mode_switch_top.v、axis_frame_pause.v，部署说明位于复现包 board/。

### R07 将模糊的视觉需求改成可验收约束

**用户反馈节选**　“你这个框改了个啥，恢复成原来那种正常的细框框，只不过颜色换成红色”；“Eagle Eye被你弄成了Eagel eEye”；“热力图上的扫描的那个视觉效果可以加回来”。

**模型处理摘要**　依据队员现场画面反馈修改 ROI 框线、标题字形与词间距、字幕行、模式和暂停状态文案；同时调整热力图扫描效果，避免遮挡重要像素。

**纠错轨迹**　模型曾把“换红色”扩展成不符合预期的粗框，并出现标题拼写问题。用户用明确反例否定前一版；后续把“看着不对”落为细框、正确字符串、远距离可读性及暂停条件等检查项。综合成功不能证明视觉呈现合格。

**证据与状态**　复现包 RTL 中 attention_targets_osd.v、attention_heatmap_osd.v、fovea_canvas_1280x720_top.v；既有复盘记录修改过程，最终 HDMI 实拍与修改前后截图尚待配齐。验收由队员在真实显示器和演示距离下完成。
## 六 从软件假设回到硬件事实

以下 R08、R09 来自既有工程复盘，模型回答均为过程摘要。现有描述可以说明排查方法，不能替代设备枚举原始日志、接线照片与演示视频。

### R08 鼠标无反应时先确认内核是否枚举

**用户反馈节选**　“好像鼠标没反应”。

**模型处理摘要**　按应用日志、Linux input、USB 驱动绑定和 Host/PHY 设备树逐层定位。复盘记载最初 /proc/bus/input/devices 无鼠标，USB 平台节点存在但驱动未绑定；修复后出现 USB Optical Mouse 和 event0。

**纠错轨迹**　如果内核尚未枚举鼠标，继续调 ROI 灵敏度或坐标映射无法解决事件缺失。排查重心转向 USB Host 与设备树配置，再回到应用事件与画面联动。设备节点出现只证明枚举成功，还需在暂停状态实际移动鼠标检查 ROI。

**人的操作与证据**　队员连接鼠标、执行串口诊断、部署设备树修正版，并观察右侧放大区域。对应 src/ps/src/mouse_roi_controller.cpp、src/ps/README_MOUSE_ROI_ZH.md、board/PROGRESS_AND_DEPLOY_ZH.md。工程复盘记载队员确认 ROI 可改变；连续操作视频待补。

### R09 连续旋转舵机不能按位置舵机验收

**提示词与反馈节选**　“我现在打算用板子控制两个舵机，做一个两自由度的仿生机械眼”；“舵机转了……我这个是360度的sg90，是不是这个问题”。

**模型处理摘要**　协助将 ROI 中心坐标映射到双路 PWM，核对 J37 引脚、Bank 电压与供电。上板观察到持续旋转后，解释连续旋转型号与普通位置舵机的控制差别。

**纠错轨迹**　原先按脉宽映射角度的假设，需要在确认实物型号后修正。PWM 可限制输出范围与变化率，但不能使连续旋转舵机获得固定角度位置控制能力。此处记录的是型号边界与方案纠偏，不能推断团队已经更换舵机或完成位置精度测试。

**人的操作与证据**　队员核对跳帽、电压、信号地、供电和机械行程。工程文件为 src/servo/roi_servo_pwm.v、servo_j37.xdc、tb_roi_servo_pwm.sv。最终采用型号及量化运动范围以实物记录为准。

### 项目已有的人机协作工作流

本项目可据现有记录归纳为带工具调用和人工实板反馈的协作流程。尚无足够记录证明使用了固定编排的多智能体系统，因此不将多名队员或多个聊天写成多智能体编排。

**流程**　队员提出目标与约束 → 模型读取工程和日志 → 拆分接口与验收条件 → 修改源码或生成脚本 → 工具执行仿真和检查 → 队员上板与观察 → 反馈反例 → 模型修正 → 版本归档并提炼 Skill。

**需求输入**　提示词尽量包含器件、工具版本、张量或视频格式、禁止修改的模块、预期产物和验收条件。R01 提供了完整范例。

**工具验证**　数值问题用完整 Golden；坐标问题回溯源图与元数据；软件移植先验证 ELF、依赖与离线链路；显示和机械交互再由实物验收。失败时回到最小可复现条件，而不是继续堆叠修改。

**版本归档**　每个被采纳的版本关联源码、模型、启动文件哈希和对应日志。不能将 QEMU、旧 CPU 基线、独立 IP 报告或用户口头反馈合并成同条件整机性能结论。

**职责边界**　模型提出和执行可检查的软件工作，团队负责实物连接、供电、板端观察与最终取舍。缺少环境或证据时记录阻塞项和后续验收任务。
